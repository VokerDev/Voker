# Voker — заметки разработчика

Это внутренний документ для тебя: как всё устроено, как расширять и как выложить на GitHub.

## Главный принцип: оркестратор, а не сборник

Voker **не хранит инструменты внутри**. Он:
1. проверяет через `shutil.which()`, установлен ли бинарник;
2. если нет — показывает команду установки;
3. если да — собирает строку аргументов и запускает через `subprocess.run()`.

Почему так, а не «всё вшить»: собрать сотни программ в один репозиторий — это уже
сделали Kali/Parrot/BlackArch, весит десятки гигабайт и упирается в лицензии и root.
Наша ценность не в наборе инструментов, а в **простом пути для новичка**.

## Структура

```
voker/
├── voker.py        # весь код (один файл — так проще для новичков-пользователей)
├── README.md       # для тех, кто скачивает с GitHub
└── README_DEV.md   # этот файл
```

Состояние (принятый дисклеймер) хранится в `~/.voker/accepted`.

## Как устроен код (что за что отвечает)

| Блок              | Отвечает за                                              |
|-------------------|---------------------------------------------------------|
| `class C` + `col`  | ANSI-цвета, фиолетовая палитра, отключение цвета         |
| `print_banner`     | ASCII-логотип                                           |
| `Action` / `Category` | модель данных одного инструмента и категории          |
| `TOOLKIT`          | **реестр всех инструментов** — главное, что ты правишь   |
| `ensure_disclaimer`| одноразовый правовой экран                               |
| `show_install_help`| подсказка по установке (выбирает apt/pipx под систему)   |
| `confirm_authorization` | подтверждение разрешения для активных действий     |
| `build_command`    | собирает список аргументов (+ sudo при `needs_root`)     |
| `run_action`       | весь цикл: проверка → ввод → подтверждение → запуск      |
| `main_menu` / `category_menu` | навигация по меню                            |
| `print_tree`       | режим `--list`                                          |

## Как добавить новый инструмент

Допиши один `Action` в нужную категорию в `TOOLKIT`. Пример — добавим `gobuster`
(поиск скрытых директорий на сайте) в «Веб-разведку»:

```python
Action(
    name="Поиск скрытых директорий сайта",
    desc="Перебирает пути по словарю и находит скрытые страницы.",
    binary="gobuster",
    install={"apt": "sudo apt install gobuster"},
    args_template="dir -u {target} -w /usr/share/wordlists/dirb/common.txt",
    prompt="Введи URL сайта",
    requires_auth=True,   # активно стучится в цель -> нужно подтверждение
),
```

Поля `Action`:
- `binary` — что искать через `which` и запускать;
- `install` — словарь `{менеджер: команда}`; `show_install_help` сам выберет apt/pipx/…;
- `args_template` — шаблон, `{target}` подставится из ввода (пусто — без ввода);
- `prompt` — вопрос пользователю (пусто — ничего не спрашиваем, как у `wifite`);
- `requires_auth` — `True` для всего, что активно воздействует на цель;
- `needs_root` — `True`, тогда перед командой добавится `sudo`;
- `note` — короткая подсказка/предупреждение.

Добавить целую **категорию** — допиши новый `Category(...)` в список `TOOLKIT`.

## Дизайн-решения (почему так)

- **Без зависимостей.** Только стандартная библиотека → «склонировал и запустил».
  Если позже захочешь красивый TUI со стрелками — посмотри `rich` / `textual`,
  но это добавит `pip install`.
- **`subprocess.run(parts)` без `shell=True`.** `parts` — это список, а не строка,
  так безопаснее (нет shell-инъекций через ввод пользователя).
- **Дисклеймер и auth-подтверждение** — не только юридически правильно, но и
  снимает вопросы у GitHub и делает проект «взрослым».

## Как выложить на GitHub

```bash
cd voker
git init
git add .
git commit -m "Voker v0.1 — MVP"
# создай пустой репозиторий на github.com, потом:
git remote add origin https://github.com/<твой-ник>/voker.git
git branch -M main
git push -u origin main
```

Добавь файл `LICENSE` (для MIT возьми шаблон прямо в интерфейсе GitHub при создании репо)
и в `README.md` замени `<твой-ник>` на свой.

## Идеи для развития (roadmap)

- Поддержка Windows (`where` вместо `which`, другие команды установки).
- Автоопределение и автоустановка зависимостей (аккуратно, с подтверждением).
- Экспорт результатов сканирования в файл/отчёт.
- Больше OSINT-инструментов (но помни: многие требуют платных API-ключей).
- Навигация стрелками через `textual`.
- Конфиг `~/.voker/config.toml` (словари для gobuster, дефолтные флаги и т.п.).
